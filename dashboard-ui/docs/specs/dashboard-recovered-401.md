# 명세: 재시도로 회복된 401 구분

- 작성일: 2026-10-01
- 상태: 확정 (2026-10-01 사용자 확인 — "1단계 ㄱㄱ")

## 목표

액세스 토큰이 만료되면 401 → 리프레시 토큰으로 재발급 → 같은 요청 재시도(성공)가 정상 흐름으로 일어난다.
지금은 그 첫 401 이 "반복되는 문제" 맨 위에 올라와 진짜 문제를 가린다.

401 을 통째로 숨기지는 않는다. 설치 현장에서는 401 이 진짜 장애 신호인 경우가 많다
(서버 시계 어긋남, 서버 간 JWT 키 불일치, 프록시가 Authorization 헤더 제거, 리프레시 API 고장).
기준은 **회복됐느냐**다 — 같은 사용자가 곧바로 같은 요청을 다시 보내 성공했으면 정상 흐름으로 본다.

## 범위 밖 (2단계)

- 서버·스타터 변경. 인증 필터에서 거부된 401 은 예외 정보가 없어 "토큰 만료"와 "토큰 없음/잘못됨"을 로그 한 줄로 구분할 수 없다.
  로그 표준의 `errorCode`(예: `AUTH_TOKEN_EXPIRED`)나 `WWW-Authenticate` 헤더가 오면 그 값을 우선 쓰는 것은 2단계.
- 보낸 요청(OUTBOUND)의 401 — 클라이언트 IP 가 없어 같은 사용자를 알 수 없다.
- 상세 패널의 "이렇게 확인해 보세요" 문구 변경.

## 수용 기준

**U** = 단위 테스트, **S** = 스토리 테스트.

- [x] A1 (U): 받은 요청 401 은 다음을 모두 만족하는 받은 요청이 있으면 "재시도로 회복됨"이다.
  같은 서비스 · 같은 클라이언트 IP · 같은 메서드 · 같은 경로(`route` 가 있으면 그 값, 없으면 ID 조각을 `{id}` 로 바꾼 경로) ·
  상태 2xx·3xx · 401 이후 30초 안(같은 시각이면 id 가 더 큰 것).
- [x] A2 (U): 클라이언트 IP 가 없거나, 30초 뒤에 성공했거나, 다른 IP·다른 경로·다른 메서드만 성공했거나, 다시 401 이면 회복이 아니다. 403 등 401 이 아닌 4xx 는 대상이 아니다.
- [x] A3 (S): 반복되는 문제는 회복된 401 을 세지 않는다. 회복되지 않은 401 은 지금처럼 보인다.
- [x] A4 (S): 기준 안내에 뺀 건수를 밝힌다 — `최근 100건 기준 · 재시도로 회복된 401 N건 제외`. 없으면 안내 뒷부분이 없다.
- [x] A5 (S): 요청 기록 표에서 회복된 401 행은 지우지 않고, 예외 칸에 `재시도 성공` 표시를 붙인다 (마우스를 올리면 설명).

## 설계 메모

- 같은 사용자 = 같은 클라이언트 IP. 프록시·NAT 뒤라 모두 같은 IP 면 다른 사람의 성공과 섞일 수 있다 — 30초 창으로 오판을 줄인다.
- 401 이 먼저 기록되고 재시도가 다음 폴링에 들어오면 잠깐 문제로 보였다가 빠질 수 있다.
